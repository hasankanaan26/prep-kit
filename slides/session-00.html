Step 01A virtual environment is a toolbox per project

Packages are other people's code that your project uses, like openai or httpx. If everything goes into the one Python on your computer, projects fight over versions. A venv is a folder with its own private Python and its own packages. The analogy: a separate toolbox per job. The best property for beginners: it's disposable. If the venv gets into a bad state, delete the .venv folder and make it again. Nothing else is lost.

Step 01Make it, switch it on, fill it

Windows

# from prep-kit/
py -3.12 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

macOS / Linux

# from prep-kit/
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Your prompt now starts with (.venv). Activate again in every new terminal.

PowerShell says "running scripts is disabled"? Run this once: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Three ideas: venv creates the folder, activate switches this terminal over to it, pip installs packages into it from a shopping list called requirements.txt. On Windows we use py, the Python launcher, because plain python often isn't on the PATH. The prep kit's list is small and takes a minute or two. The course gets its own venv and a much bigger list in step 08: one toolbox per project, which is the point of the previous slide.

Step 02An API call is a request and a response

GET reads something. POST creates or changes something. JSON is text that looks like a Python dict.

An API is a menu another program offers you. You send a request, you get a response. Every request has a method (GET to read, POST to change), a URL, headers (notes on the envelope, like your key), and sometimes a JSON body. Every response has a status code and usually JSON. A call to a language model is exactly this shape: a POST with JSON in and JSON out. That's why we spend half an hour here.

Step 02Four status codes you'll actually see

200 OK

Here's what you asked for.

404 Not found

I understood you, but that thing doesn't exist.

429 Too many

Slow down. You'll meet this on free LLM tiers.

500 Server error

Something broke on my side, not yours.

A 404 is not a crash. The server answered fine; it's telling you something. Good code reads the status and decides what to do.

Four codes are enough for this month. 429 matters because free tiers on Gemini and OpenRouter rate-limit you: the fix is to wait, not to hammer it. 500 matters because real APIs fail, and the course makes them fail on purpose (the X-Chaos header on the mock API) so they can practise handling it in Session 5.

Try itA real API, running on your laptop

# terminal 1, from prep-kit/ (leave it running)

# terminal 2, from prep-kit/
py code\hello_api.py
  1. Open http://localhost:9000/docs: every endpoint, with a "Try it out" button.
  2. hello_api.py sends five requests: an order, a missing order (404), a refund, the same refund again, and a forced failure (500).
This is a small fake version of the Nimbus order system, and the course uses it in every week. Step 02Same key, same refund

=== 3. Issue a refund
POST http://localhost:9000/refunds        Idempotency-Key: prep-kit-1f2a9c3e
-> status 200 OK      {"refund_id": "R-26762c6f", "amount_usd": 79.99}

=== 4. Retry with the SAME key
POST http://localhost:9000/refunds        Idempotency-Key: prep-kit-1f2a9c3e
-> status 200 OK      {"refund_id": "R-26762c6f", "amount_usd": 79.99}

A receipt number on a bank transfer. Hand the clerk the same slip twice and you pay once, because they've already seen that number.

The caller picks a unique key for "this one refund". A retry after a timeout reuses it, so the customer is refunded once. That's called idempotency.

This is the one API idea worth naming today, because money is involved. Networks time out. If a refund request times out, you don't know if it happened, so you retry. Without a key, a retry can refund twice. With the key, the server recognises the request and returns the first refund. Session 5 builds the real refund tool on this. Don't go deeper today; the name and the picture are enough.

Quick checkAPIs

  1. You ask for order O-00000 and get a 404. Is the API broken?
  2. A refund request times out. Why is it safe to retry with the same Idempotency-Key?
  3. Your script prints Virtual env : NO. What did you forget?
Answers. 1: No. The server answered correctly: that order doesn't exist. 404 is information, not a failure. 2: The server remembers the key. If the first request went through, it returns that same refund instead of making a second one; if it didn't, the retry does it. Either way the customer is refunded exactly once. 3: Activating the venv in this terminal (.venv\Scripts\activate, or source .venv/bin/activate).

Step 03Keys never go in your code

The .env file

GEMINI_API_KEY=AIza...
GEMINI_MODEL=gemini-3.5-flash-lite

python-dotenv reads it at startup and Python sees each line as an environment variable.

The .gitignore file

# Secrets
.env

Git never sees .env, so you can't commit it by accident. The repo ships .env.example with the values empty.

Bots scan public GitHub for leaked keys within minutes. A key in your code is a key on the internet.

An API key is your username and password in one string, attached to your credit card. Environment variables are named values the operating system hands to each program. Typing them every time is tedious, so projects keep them in a .env file, and a small package reads it. Show show_env.py: it reports which keys are set and how long they are, never the value, and warns about the two classic paste mistakes, a trailing space and quote marks.

Step 03Four habits that save you money

  1. Never paste a key into code, a chat (AI assistants included), a screenshot or a slide.
  2. Set a monthly spending limit the day you create a paid key.
  3. Leaked a key? Revoke it in the provider's dashboard and make a new one. It takes a minute.
  4. One key per project, so you can revoke one without breaking the others.

Two .env files, on purpose: prep-kit/.env for free practice keys, resolvo-workshop/.env for the course key.

The spending limit is the one to stress. A loop with a bug can make thousands of calls while you're at lunch; a limit turns that into an annoyance instead of a bill. And revoking is not a big deal: people leak keys all the time, and the fix is boring and fast. The two .env files keep practice and course separate, so nothing in the prep kit can change how the course code behaves.

Step 04An LLM call is just another API call

You send

{
  "model": "gemini-3.5-flash-lite",
  "messages": [
    {"role": "system",
     "content": "Keep answers short."},
    {"role": "user",
     "content": "What is an API?"}
  ],
  "temperature": 0.2
}

You get back

{
  "choices": [{"message": {
    "content": "A set of rules that
     lets programs talk..."}}],
  "usage": {
    "prompt_tokens": 31,
    "completion_tokens": 24
  }
}

system sets the rules · user asks · temperature is randomness (0 = steady) · usage is what you pay for

Connect it back to step 02: a POST, JSON in, JSON out. The model field picks which model. Messages is the conversation so far: the system message sets the rules, the user message asks. Temperature controls randomness: near 0 you get the same answer most times, higher gives more variety. The response has the reply and a usage block with token counts, which is what the bill is based on. Tokens get their own step later.

Step 04One SDK, three addresses

A provider is an address plus a key. Change those two and the same code talks to a different company's model.

This is the one idea to take from step 04. Most providers now offer an OpenAI-compatible API, meaning the same request shape OpenAI made popular. So the openai Python package talks to all of them; only base_url, the key and the model name change. In prep-kit/code/providers.py that's a three-row table. The Resolvo code does the same thing in a file called llm.py: one place knows about the provider and the rest of the program never does. They'll meet llm.py in Session 2.

Step 04All the code it takes

from openai import OpenAI

client = OpenAI(base_url="https://openrouter.ai/api/v1", api_key=key)

response = client.chat.completions.create(
    model="openrouter/free",
    messages=[{"role": "system", "content": "Keep answers short."},
              {"role": "user", "content": "Explain an API in one sentence."}],
)
print(response.choices[0].message.content)
print(response.usage.prompt_tokens, response.usage.completion_tokens)

The kit wraps this in code/chat.py with a --provider switch and friendly error messages.

Read it line by line: make a client pointed at an address with a key, send a model name and messages, print the reply and the two token counts. That's it. Everything clever in the next four weeks happens around this call, not inside it. chat.py adds a timer and turns the usual errors (missing key, 401, 429, 404) into a sentence with a fix.

Step 05A model on your own laptop

ollama pull llama3.2          # about 2 GB, 3 billion parameters
py code\chat.py --provider ollama "Say hello in five words."
Your laptop hasTry
8 GB of memoryllama3.2 (2 GB)

The graphics driver is the usual cause. Quit Ollama, then run it on the CPU: $env:CUDA_VISIBLE_DEVICES="-1"; ollama serve

The first call is slow, 10 to 20 seconds, because the model loads into memory; later calls are much faster. Then the party trick: turn off Wi-Fi and run it again. It still works. The crash on the slide is real: we hit it on a Windows laptop while building this kit, and running on the CPU fixed it. If a laptop can't run a model at all, that's fine; Gemini and OpenRouter cover everything else.

Step 06Models read tokens, not words

py code\count_tokens.py

Ticket T-1001: 217 characters, 40 words, 47 tokens

'I' | ' ordered' | ' the' | ' wireless' | ' headphones' | ' two' | ' weeks' |
' ago' | ',' | ' order' | ' #' | '482' | '91' | '.' | ' They' | ' arrived' | ...

A token is a chunk of text: often a short word, sometimes part of a word or a number. English is about 3 tokens per 4 words.

The order number 48291 became two tokens. The model never sees it as one thing.

This runs offline, nothing is sent. Before a model sees text, a tokenizer cuts it into chunks and turns each into a number. Point at 482 and 91: that's part of why models sometimes garble long numbers when they copy them. Other languages, Arabic included, usually take more tokens for the same meaning, so they cost more. Session 1 goes much deeper on this.

Step 06Same request, different price per language

The same requestWordsTokens
I want a refund for my order77
أريد استرداد المبلغ لطلبي410
بدي رجّع المصاري37

The tokenizer learned mostly from English, so other languages get cut into more pieces. refund is 1 token; استرداد is 3.

Try yours: py code\count_tokens.py --text "your sentence"

Moved here from Session 1. Ask who has built a product for Arabic-speaking users. English: 7 words, 7 tokens. Modern Standard Arabic: 4 words, 10 tokens. Lebanese dialect: 3 words, 7 tokens. So an Arabic ticket costs more, takes a little longer, and fills more of the model's space for that call. Estimate costs with your real customers' language, not English test data. Counts are from the GPT-4o tokenizer (o200k_base); other providers' tokenizers differ, and the gap has narrowed but not closed.

Step 06What one ticket costs

Read ticket T-1001 (47 tokens) and write a 150-token reply:

ModelPer ticketPer 10,000 tickets
gpt-4o-mini$0.000097$0.97
gemini-3.5-flash-lite (paid tier)$0.000389$3.89
gpt-4o$0.001618$16.18
  • Priced per million tokens. Output costs more than input.
  • One call is a fraction of a cent. The choice of model is a 16× difference in the bill.

Prices checked October 2026. They change: always check the provider's pricing page.

The arithmetic is input tokens times input price plus output tokens times output price, divided by a million. count_tokens.py does it for them. The point isn't the exact figures; it's that the model choice dominates the bill, and the reply usually costs more than the question. compare.py then sends one ticket to every provider they've set up and prints the time each took. Times change from run to run, which is why Session 1 measures speed over many calls.

Step 07A taste of Resolvo: the model suggests, your code decides

py code\taste_of_resolvo.py --provider gemini

--- T-1002: Hi, checking on order O-58204 (SoundBar Mini). It says shipped...
    OK      {'category': 'shipping_delay', 'priority': 'low', 'sentiment': 'calm'}

1. Valid JSON?

Not "Sure! Here's the JSON…"

2. An object?

A dict, not a list or a string.

3. Allowed values?

Every field from the list.

Anything that fails is printed as REJECTED with the raw reply. It is never used.

This is a small version of checkpoint 01, with the same labels: category, priority, sentiment. The prompt says "reply with ONLY a JSON object", and models still say "Sure! Here's the JSON", wrap it in a code fence, or invent a category. parse_reply in the script checks every reply. The sentence to leave them with is the title: the model suggests, your code decides. That rule runs through the whole course, especially for refunds.
