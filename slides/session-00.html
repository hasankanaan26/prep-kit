Step 01A virtual environment is a toolbox per project

A virtual environment (venv) is a folder with its own Python and its own packages, one per project.

A quick word on packages first. Packages are other people's code, like openai or httpx, that you install and then import. Now look at the left box. If you install everything into the one Python on your computer, every project shares one shelf. Project A wants openai 2, project B wants openai 1, and one of them breaks.

A virtual environment, a venv, fixes that. It's a private copy of Python with its own shelf of packages, one per project. Think of it as a separate toolbox for each job. And because it's just a folder, there's nothing precious about it.

[Watch out: venv in a bad state? Delete the .venv folder and make it again. Nothing else is lost.]

Step 02An API call is a request and a response

GET reads something. POST creates or changes something. JSON is text that looks like a Python dict.

An API is a menu another program offers you. Here's the whole shape of a call. Your code, on the left, sends a request: a method like GET, a URL, some headers, and for a POST a JSON body. The order API on the right sends back a response: a status code and some JSON. Headers are the notes on the envelope, and later that's where the API key, the password for the service, travels.

The reason we spend time on this today is that a call to a language model has exactly this shape. It's a POST, JSON in, JSON out. Nothing magic about the transport.

Four status codes, and you'll see all four this month. 200 means here's what you asked for. 404 means I understood you, but that thing doesn't exist. That's not a crash: the server answered perfectly well, it's telling you something. 429 means slow down, and you'll meet it on the free LLM tiers; the right move is to wait, not to hammer it. 500 means the other side broke, not you.

Step 02Sending the same refund twice pays out once

# hello_api.py, blocks 3 and 4, trimmed. The key on the right is set in the code.
=== 3. Issue a refund
POST http://localhost:9000/refunds        Idempotency-Key: prep-kit-1f2a9c3e
-> status 200 OK      {"refund_id": "R-26762c6f", "amount_usd": 79.99}

=== 4. Retry with the SAME key
POST http://localhost:9000/refunds        Idempotency-Key: prep-kit-1f2a9c3e
-> status 200 OK      {"refund_id": "R-26762c6f", "amount_usd": 79.99}

A receipt number on a bank transfer: hand the clerk the same slip twice and you pay once.

The caller picks one key for "this refund". A retry after a timeout reuses it, so the customer is refunded once. That's called idempotency.

Look at blocks 3 and 4. Same refund request, sent twice, same refund ID back. Here's why that matters. Your code asks for a refund and the request times out. Did it happen or not? You don't know. So you retry. Without a key, that retry can refund the customer twice. With the same Idempotency-Key, the server recognises the slip and returns the first refund instead of making a new one.

It's like a receipt number on a bank transfer: hand the clerk the same slip twice and you pay once. The caller picks one key, then reuses it on every retry of the same refund. That's idempotency.

Step 03Keys never go in your code

The .env file

GEMINI_API_KEY=AIza...
GEMINI_MODEL=gemini-3.5-flash-lite

python-dotenv reads it at startup and Python sees each line as an environment variable.

The .gitignore file

.env

Git never sees .env, so you can't commit it by accident. The repo ships .env.example with the values empty.

Bots scan public GitHub for leaked keys within minutes. A key in your code is a key on the internet.

Think of an API key: it's your username and password in one string, with your credit card attached. So it never goes in your code. It lives in a file called .env, one line per value, and python-dotenv reads that file when your program starts. Python then sees each line as an environment variable, which is a named value the operating system hands to each program.

The other half is .gitignore. It tells Git to never even look at .env, so you can't commit it by accident. The warning at the bottom is not an exaggeration: bots scan public GitHub for leaked keys within minutes.

Step 04An LLM call is just another API call

You send

{
  "model": "gemini-3.5-flash-lite",
  "messages": [
    {"role": "system",
     "content": "Keep answers short."},
    {"role": "user",
     "content": "What is an API?"}
  ]
}

You get back

{
  "choices": [{"message": {
    "content": "A set of rules that…"}}],
  "usage": {
    "prompt_tokens": 31,
    "completion_tokens": 24
  }
}

system sets the rules · user asks · usage: how many tokens (chunks of text, step 06) went in and out. That's the bill.

Here's the payoff from step 02. A call to a large language model, an LLM, is the same POST: JSON in, JSON out. On the left is what you send: a model name and a list of messages. The system message sets the rules, the user message asks the question.

On the right is what you get back. The reply is tucked inside choices, and then there's usage: two token counts, what you sent and what the model wrote. That's what the bill is based on. For now, a token is a chunk of text; step 06 shows exactly what that means.

Step 04All the code it takes

import os
from dotenv import load_dotenv
from openai import OpenAI

# 1 · the address and the key (load_dotenv reads .env, as on the secrets slide)
load_dotenv()
key = os.environ["OPENROUTER_API_KEY"]
client = OpenAI(base_url="https://openrouter.ai/api/v1", api_key=key)

# 2 · one call: a model name and the messages
response = client.chat.completions.create(
    model="openrouter/free",
    messages=[{"role": "system", "content": "Keep answers short."},
              {"role": "user", "content": "Explain an API in one sentence."}],
)
# 3 · the reply, and the two token counts
print(response.choices[0].message.content)
print(response.usage.prompt_tokens, response.usage.completion_tokens)

A minimal version to read, not a file in the kit. The kit's code/chat.py does the same, with a --provider switch and friendly error messages.

Here's all the code it takes; follow the numbered comments. One: a client, which is an address and a key. The key comes from .env, the way the secrets slide showed. Two: one call, with a model name and a list of messages, the system rule and the user question. Three: you print the reply, and two token counts. That's it.

Everything clever in the next four weeks happens around this call, not inside it: what goes into the messages, what you do with the reply, and how you check it. The kit wraps this in chat.py so you get a provider switch and readable error messages.

Step 06Models read tokens, not words

py code\count_tokens.py          # output trimmed

Ticket T-1001: 217 characters, 40 words, 47 tokens

The first 20 tokens, as the model sees them:
'I' | ' ordered' | ' the' | ' wireless' | ' headphones' | ' two' | ' weeks' |
' ago' | ',' | ' order' | ' #' | '482' | '91' | '.' | ' They' | ' arrived' | ...

A token is a chunk of text: often a short word, sometimes part of a word or a number. English is about 4 tokens per 3 words.

The order number 48291 became two tokens. The model never sees it as one thing.

Here's what a token is. Models don't read words; they read tokens. A tokenizer cuts text into chunks and turns each chunk into a number, and the model only ever sees those numbers. Often a chunk is a short word with its leading space, sometimes it's part of a word or a number. Ticket T-1001 is 40 words but 47 tokens.

Now look at the highlighted bit: the order number 48291 became two tokens, 482 and 91. The model never sees that number as one thing. That's part of why models sometimes garble long numbers when copying them. Keep that in mind every time Deskhand handles an order ID.

2. An object?

A dict, not a list or a string.

3. Allowed values?

Every field from the list.

Anything that fails is printed as REJECTED with the raw reply. It is never used.

This is the rule the whole course runs on: the model suggests, your code decides. taste_of_resolvo.py asks a model to sort real tickets into a category, priority and sentiment, and asks for only a JSON object back. Then the code checks the reply three ways before trusting it. Is it valid JSON? Models still say "Sure! Here's the JSON", or wrap it in a code fence. Is it an object, not a list or a string? And is every value from the allowed list? Models invent categories.

Anything that fails is printed as REJECTED, and it's never used. That matters most later, when the action is a refund.
